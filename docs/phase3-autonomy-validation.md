## 自动验证中发现并修复的问题

1. **实际请求数不能只数 Agent 逻辑调用。** 固定 Provider 内部还有错误处理/续调路径。现在在同一个已配置客户端的实际 `chat.completions.create` 边界计量，预占后再I/O；原生payload清理后的最终消息、工具和参数进入审计。客户端内部重试必须为0，Agent总尝试为1，不切第二Provider。使用真实固定Provider与OpenAI SDK、`httpx.MockTransport`验证；这是模拟HTTP响应，不是真实DeepSeek。
2. **插件重载不能丢失调用计量。** SDK方法包装保存原方法，按当前ContextVar重新绑定，避免旧插件实例包装残留；被动请求不进入主动计数。
3. **同一补充父消息可能换交流ID再次创建。** 持久补充预检和事务预占同时检查 `parent_attempt`，因此兴趣→unknown结果→新交流ID不能绕过一次限制；失败和重启不退还次数。
4. **模型选择send不等于送达。** `ready_to_send`之后独立记录Guard的sent/failed/unknown/cancelled及尝试ID，保留原模型控制和解析结果；不能把部分成功或未知回执改成整轮成功。
5. **“有工具来源”不等于当前外部断言有依据。** 外部事实通过显式 `source_refs` 关联本机会实际工具来源或当前许可的选中口袋来源。无来源断言保留external_fact类型、unshared和unverified状态，不改名为假设以绕过检查，不自动成为ready/shared。已获取来源也只标明retrieved_not_fact_verified。
6. **延期与过期分开记录。** 正数延期可变，0和错误控制不泄漏为聊天正文；超过候选生命周期保留模型defer及最终不可执行原因，不能冒充模型skip。

### 需求映射中的实施边界

- **普通交流的延迟补充窗口较配置更窄。** 5–60分钟是候选年龄范围，普通交流仍遵守原生45分钟私聊空闲门槛和300秒检查周期；因此在没有新输入、其他条件均允许时，通常只能在约45–60分钟的剩余窗口考虑，并不保证第5分钟、某个固定时刻或每次聊天后都补一句。补充只例外通过普通主动发送冷却，不绕过空闲、时段、暂停、忙碌、每日次数及已关闭话题控制。本轮未调低空闲门槛。
- **自身偏好是五类原生接口接通。** 当前只处理音乐`music`、饮食`food`、媒体`media`、游戏`game`、审美`aesthetic`中的明确可识别表达，每类日常召回最新一条，最多5条；一次确认表达即可记录。它不会保证任意兴趣或一般观点都能提取、合并和修订，也没有完整Self State。只从Guard确认正文派生，保留来源和撤销状态，不把待分享发现、失败/unknown尾部或视觉推测写成已表达偏好或用户事实；未来完整自身记忆通过`current()`/`prompt()`薄接口衔接。
- **工程通过和内容质量分开。** 上述组件与完整宿主通过证明对应程序路径；真实随机样本、来源支持和用户自然度分别评估。真实质量仍按PARTIAL/待本人评价记录，不能把少数成功样本、发送率提高或所有机会流程完成解释为稳定质量已全部通过。工具来源关联也不是逐断言事实核验，仍可能出现套话、无意义追问或超出来源的表述，具体样本与修复对照留在后面的真实审阅记录。
