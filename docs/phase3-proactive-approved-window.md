## 计算与安装

`integrations.phase3_runtime.proactive.approved_window_after_passive(passed_at, passive_passed=True)` 是纯函数，不读当前时钟、不修改配置、不启动服务。未明确通过或未提供带时区的 ISO 时间时拒绝计算。

返回 `passive_passed_at`、`window_start_iso`、`window_end_iso`，统一明确为 `+08:00`，以及可直接写入候选的 `proactive_window`：Unix 开始/结束秒、`max_per_day=2`、`cooldown=14400`、`quiet_hours=[23,9]`。

“下一个 09:00”严格晚于通过时间。当天 08:59:59 通过则当天 09:00 开始；恰好 09:00 或之后通过则次日 09:00 开始。结束时间是开始时间加 72 小时，结束瞬间不再允许主动。日期跨月、跨年和不同输入时区由标准时间库处理。

执行代理应先保存真实被动 PASS 的证据与时间，再生成并审查该窗口，将绝对开始/结束时间列入最终报告。仍需使用已批准的原生目标 capability 迁移和既有安全启动流程。磁盘 Private 配置始终保持日限额 0、生成关闭；runtime 完成策略检查后才在实例内启用。被动候选的 `proactive=false` 不受新增窗口校验影响。

## 到期与安全边界

每次生成、生成结束、发送前都检查绝对窗口和静默时段。到期后新请求立即拒绝；下一个既有原生 scheduler cycle 会把实例的主动日限额和生成开关归零，不新增定时器，也不停止被动缓存维护。到期后重启保持主动关闭，普通被动服务仍可启动。

已经交给平台的发送不能撤回；已经开始的模型调用受原有总超时限制，结束后过期结果丢弃。窗口内的 2 次是上限，不保证每天必发。原生更严格的时段、候选质量、用户忙碌和暂停控制继续生效。
