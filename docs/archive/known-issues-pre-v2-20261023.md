## Phase 1 确认且仍需保留的限制

1. **Phase 1 没有真实 QQ、DeepSeek 与生产部署验证。** 离线验收仅使用网络隔离的 OneBot/模型模拟对端；不能证明 QQ 风控、登录态长期在线、模型中文质量或公网网络可用。Phase 2 的实际部署、聊天与恢复证据单独记录，不改变这一历史范围。
2. **授权边界。** MemoryCompanion、PrivateCompanion 未找到项目级许可证，只作原样本地依赖评估，不纳入本仓库源码或镜像分发。Recorder 的 LICENSE 为 GPLv3、README 却称 AGPL，分发前需澄清。NapCat/SnowLuma 属限制性许可，未来使用方式需重新核对。
3. **Recorder 不自动覆盖出站。** 实测入站、重复记录、重启与恢复；普通模型回复没有 bot sender 记录。本项目 Guard 补齐本阶段私聊非流式单段文本的入站、出站及准确发送状态。Phase 2 最终生产样本为入站 7、出站状态 8（sent=7、failed=1、pending=0、unknown=0）；唯一 failed 是空文本在 QQ 发送前被拦截，成功的 7 条非空回复均有归档。它不声称覆盖主动发送、工具发送、所有媒体和分段输出。超时状态为 `unknown`，不自动补发。
4. **连续消息不是严格 FIFO。** AstrBot 在会话锁前有异步处理，网络到达顺序可能与模型处理顺序不同。实际验证每条中文/Emoji输入恰好处理一次、上下文按实际处理顺序累积、最终原文/历史/回复完整，无丢失覆盖。本阶段未宣称完成防抖、自然消息合并或严格到达顺序保证。
5. **Future Tasks 一次性失败删除。** 原生定时一次任务在 `finally` 删除任务，即使执行失败；本轮5项真实调度测试确认该行为。未实现生产提醒补发或可靠送达，不将其算成可靠提醒通过。自然语言模型选择提醒工具未验证。
6. **DeepSeek 文档确认与真实调用须分开记录。** Phase 1 当时未在线确认官方型号；Phase 2 已核查[官方型号说明](https://api-docs.deepseek.com/quick_start/pricing/)和[图片输入要求](https://api-docs.deepseek.com/guides/vision/)，`deepseek-flash` 支持图片，`deepseek-v4-pro` 不支持。本次真实账户的 8 项有限直接 API 测试已覆盖 Flash/Pro、图片与工具往返并通过，QQ 文本上下文及单张图片样本也由用户确认；这些不代表普遍回复质量或所有图片场景。不能把源码字符串、Mock 或原有 4 项无密钥/无效输入测试视为真实 API 成功。不为图片测试擅自更换服务或开通付费产品。
7. **P1 记忆与陪伴范围。** Memory 的手工写入、检索、当前轮注入、双向时间线捕获已测；自动LLM抽取、embedding及长期记忆质量未测。Private 的昵称/状态/隔离/持久化已测；主动消息、虚构日程、外部桥接在测试配置关闭，没有长周期陪伴质量结论。共同加载和一次实际请求的上下文可观察，不等于所有桥接能力通过。
8. **Phase 1 未做 WebUI 页面验收。** Phase 1 为 headless，关闭仪表盘监听；Phase 2 已通过 SSH 隧道使用原生 Dashboard 登录与 Key 输入，以及 NapCat 扫码界面，未重新开发管理后台。这些使用记录不等于全部后台页面与管理操作验收。
9. **上游离线后台告警。** AstrBot启动仍尝试下载渲染端点及模型元数据；在 `network=none` 下请求失败并写日志，文本链路可运行。未绕过网络隔离或修改上游；这些失败不能误算成外网访问成功。
10. **构建平台范围。** 验证 `linux/amd64`、Python 3.12；其他CPU/系统尚未验收。初次构建/获取外部源需要受许可的GitHub/PyPI/Docker网络，运行验收阶段无外网。

## 已修复的项目集成问题

- 将外部运行根加入 Python 模块路径，解决 `data.plugins` 导入失败。
- 兼容 AstrBot 写出的 UTF-8 BOM；将框架不保留的项目元数据放到独立 `phase1.json` 侧车，真实重启验证。
- 停机前等待真实数据库提交，避免刚收到发送确认就中断仍在持久化的流水线。备份只在写入者已停止时执行。
- 不用上游 `after_message_sent` 钩子判成功，因为该钩子在失败后也可能触发；公开 `event.send()` 的结果进入最小发送状态表。
- 在其他插件业务前持久去重，防止相同ID再次触发模型和记录。
- Recorder 查询命令原本能跨用户查询，通过 AstrBot 公开命令权限API收紧为管理员；Phase 1 合成 OneBot 事件驱动真实框架的非管理员负例通过，真实 QQ 非授权账号负例仍未测试。
- 固定兼容依赖及只读镜像源码权限；未修改任何第三方源文件。早期诊断记录保留在本机 `evidence/runs/`，最终报告只引用最终选定运行，并如实保留上述P1缺口。
- Phase 2 首启时上游把 `request_max_retries=0` 规范化为 `1`，导致启动策略阻断。经固定源码确认，此字段计入首次传输，生产配置与门禁改为 `1` 并回归通过；不改上游代码，不放开传输重试。内容兼容修复另有循环，不能宣称整个框架只有一次模型调用。
- Phase 2 安全接收 Dashboard Key 时保留既有数据文件的 UID/GID 和权限，避免 root 原子替换后 UID10001 无法读取；已有不同 Secret 拒绝覆盖。生产凭据与账号标识只保存在受保护的运行配置。
- 发布准备复核发现快捷登录默认模式仅凭唯一缓存候选，可能把它保存为与当前在线会话不同的账号。已增加保存前的在线身份一致性检查，并用合成测试覆盖不匹配、无效身份、身份请求失败及重连状态；失败时不保存、不追加登录。线上验收使用的 `--save-current-session` 模式已有身份核验，行为保持不变。

当前剩余事项是真实非授权账号负例、长期观察、远端模型超时恢复、云安全组核对，以及需单独授权的服务器重启和内核更新。第三方使用及分发边界持续有效，固定镜像、运行策略、日志保护与本轮私聊/归档/隔离恢复的通过范围见 [Phase 2 实测记录](phase2-validation.md)。基础通信成功不代表自动记忆、主动聊天、可靠提醒或严格消息顺序已达到 Phase 3 可用要求。
